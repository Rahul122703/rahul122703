<details>
<summary><b>&nbsp;Case notes — the decisions behind each build</b></summary>

<br/>

### RahulMart · e-commerce without a backend server

- **Problem** — A storefront needs products, orders and payments, but standing up and paying for a server to host a catalogue is the wrong trade.
- **Approach** — Treat Airtable as the datastore and Netlify functions as the API, so product data changes without a redeploy.
- **Architecture** — React client → Netlify serverless functions → Airtable records. Stripe handles the payment path, OAuth handles identity.
- **Highlights** — Listings editable outside the codebase, filter/sort/search composed over a single product query, persistent dark mode, login and order history.

### Pollverse · the mood behind the vote

- **Problem** — A tally tells you which option won and nothing about how the room felt, or whether that feeling shifted.
- **Approach** — Let people answer anonymously, analyse the sentiment of what they write, and plot it across time rather than freezing it at one number.
- **Architecture** — Flask app → SQLAlchemy models for polls, users and responses → sentiment processing → Matplotlib output. Werkzeug for password hashing, email for notifications.
- **Highlights** — OTP-verified accounts with a genuine incognito path, per-user poll tracking, and sentiment trends instead of point-in-time results.

### ShareBro · sharing files without handing them to a chat app

- **Problem** — Sending documents through messaging apps means compression, size caps and no control over who keeps a copy.
- **Approach** — Anonymous uploads for speed, accounts for control, and rooms when a group needs the same set of files.
- **Architecture** — Next.js app → Prisma schema over SQLite → JWT-authenticated routes → Socket.IO for room chat, deployed on Render with SEO in mind.
- **Highlights** — Two access models in one product, room-scoped sharing, Gemini AI wired in for assistance.
- **Lineage** — Grew out of ShareSense, the earlier Flask version that handled 50+ files per upload regardless of type.

### Student Dashboard · one record, many views

- **Problem** — Courses, messages, progress and settings all read and write the same student state; per-module local state drifts apart within a week.
- **Approach** — One Redux Toolkit store, slices per domain, components that only render what selectors hand them.
- **Architecture** — Vite + React → slice-based store → Axios data layer → Recharts and a contribution-style heatmap for progress.
- **Highlights** — Resume upload with improvement tracking, message pagination with read/delete/reply, dynamic category filters, real-time notification state, layout that holds up on a phone.

## `// 10 · HOW I WORK`

- **Auth is part of version one.** Every project I ship has a login worth attacking — OTP, JWT, OAuth — because retrofitting access control means rewriting the data model.
- **Deploy early, then keep it up.** A live URL exposes what localhost hides: cold starts, upload limits, CORS, environment drift.
- **Pick the boring backend.** Airtable and serverless functions for a storefront, Flask and SQLAlchemy for a poll engine. The stack should match the problem's actual size, not its ambition.
- **Centralise state only when views start sharing it.** Redux Toolkit earns its setup on a dashboard with six modules; it's overhead on a landing page.
- **If I do it twice, I script it.** Applications, data extraction, repetitive form work — that's what Selenium and BeautifulSoup are for.
- **Write it so it can be handed over.** Branching strategy, reviewed pull requests, readable components: the work has to survive someone else opening it cold.
